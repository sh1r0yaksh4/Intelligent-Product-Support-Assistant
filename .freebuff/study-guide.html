1. Executive Summary

One paragraph version of what this system does and why it matters.

The Intelligent Product Support Assistant is a chat-based system that answers customer questions across two domains: hardware troubleshooting (routers, headphones, IoT devices) grounded in verified product documentation, and general customer support (orders, returns, shipping, account management) grounded in curated FAQ data. It combines four evidence tiers — local product manuals, approved historical Q&A, general support FAQs, and live Google Search — with a strict zero-hallucination guardrail that forces the system to escalate to official support when it can't verify an answer.

This matters because wrong hardware instructions can brick devices. Providing an incorrect reset sequence, voltage rating, or firmware version for a router can permanently damage it. A typical chatbot that "sounds confident" is actively dangerous in this domain. Our system is designed to be reliable: it either cites a verified source or it says "I don't know."

What the system does in three sentences

A customer asks a question in a Streamlit chat interface. The system first classifies the question domain (product support vs. general support), then routes to the appropriate pipeline: hardware questions search product manuals and approved memory, while account/order/policy questions search curated FAQ data. Both paths generate grounded answers citing exact sources — or safely escalate to support if they can't verify.

2. Problem Statement & Motivation

Why this system needs to exist, and why naive approaches fail.

2.1 The Core Problem

Consumer electronics support is high-stakes. A TP-Link Archer AX21 V1.0 has completely different firmware, LEDs, and reset behaviors than a V2.0 or V3.0. Generic LLMs trained on the internet mix up these versions, fabricate pinout sequences, and invent reset procedures that don't exist — sometimes damaging the very devices users are trying to fix.

2.2 Why Naive Approaches Fail

ApproachWhat It DoesWhy It Fails Here
Direct LLM query Ask ChatGPT/Claude the question directly No grounding in official docs. Mixes up hardware versions. Confidently wrong answers. No citations.
Prompt stuffing Paste entire manuals into every prompt Context window limits. Expensive. Slow. Still no version-awareness or relevance gating.
Fine-tuning Bake knowledge into model weights Needs massive data. Changed manual = retrain. No citations possible. Months of work.
Basic RAG Vector search → generate Doesn't know when it doesn't know. Still hallucinates if retrieval misses. No version filtering.

2.3 What Makes This System Different

Hardware-Version Awareness

Filters documents by exact hardware revision (V1 vs V2 vs V3). A reset procedure for V1 won't accidentally be applied to V2.

Zero-Hallucination Guard

Dual safety net: the model is instructed to emit NOT_FOUND: if uncertain, AND a similarity score threshold gates retrieval confidence.

Self-Improving Memory

User feedback promotes verified Q&A pairs into a secondary vector collection — improving future responses without overwriting official docs.

Multi-Turn Clarification

Instead of guessing, the system asks one targeted follow-up question when product or issue details are ambiguous.

3. Architecture Overview

The high-level design and its key architectural decisions.

3.1 Why RAG, and Why This Shape

Retrieval-Augmented Generation (RAG) keeps documents in an external index and retrieves only the relevant passages for each question. This is the right fit because:

  • Scales to whatever source material you add — more manuals, more FAQs, more support pages.
  • Updates instantly — re-index a changed manual and every future query sees the new version.
  • Inspectable — you can see exactly which passages the system retrieved and why it answered the way it did.
  • Decisions per query — the system can check what it actually retrieved and decide whether it genuinely knows the answer.

3.2 The Two Pipelines

The architecture cleanly separates an offline indexing pipeline (runs once, or when docs change) from an online query pipeline (runs per message). This separation means re-indexing a changed manual never touches the chat logic, and debugging "the answer was wrong" starts by checking which pipeline failed.

Figure 1: The dual-path architecture. The assessor classifies questions into product_support or general_support, routing each to its own retrieval pipeline.

3.3 The Core Architectural Invariant

The Grounded-or-Escalate Principle

This is the single most important architectural decision. Two independent safety signals prevent hallucination:

  1. Model self-admission: The system prompt instructs Gemini to begin its response with NOT_FOUND: if the evidence is insufficient. We check for this prefix in the raw output.
  2. Retrieval confidence gate: The best similarity score must exceed MIN_DOCUMENT_SIMILARITY (0.42). Below this threshold, we fall through to web search or escalate.

If either signal fires, the system returns a safe escalation message pointing the user to official manufacturer support — it never guesses.

Every technology choice and why it was made.

4.1 Why Not LlamaIndex or LangChain?

The initial plan proposed LlamaIndex. The actual implementation uses a custom orchestration layer because:

  • Full control: Every branching decision (assess → clarify, retrieve → gate, generate → escalate) is explicit Python — no framework magic to debug.
  • Explainability: When presenting, every line of the pipeline is something you wrote and can walk through.
  • No abstraction leaks: LlamaIndex's query engine abstracts away the retrieval→generation boundary. Here, that boundary is exactly where the most important decision happens.
  • Dependency minimization: Fewer packages to install, fewer version conflicts, fewer surprises.

4.2 Why Gemini Specifically?

The Google Search Grounding Advantage

The single biggest reason to use Gemini over Claude or GPT is the native Google Search grounding tool. When local documentation is insufficient, Gemini can search the web and cite its sources — all within a single API call. With other models, you'd need to build a separate search integration, handle the API, parse results, and inject them into the prompt. Here, it's one function call: search_grounded_answer().

5. Component Deep Dive

Every module in the system, what it does, and how it connects.

5.1 The Core Pipeline (rag/chatbot.py)

The ProductAssistant class is the central orchestrator. Its answer() method executes the entire pipeline in a single synchronous call:

  1. Assess: Calls assess_conversation() — Gemini decides if we need clarification.
  2. Formulate: Builds a standalone query from product name + version + recent history + question.
  3. Retrieve: Queries both ChromaDB collections (docs + memory).
  4. Gate: Checks if the best local chunk score ≥ threshold.
  5. Generate or Fallback: Strict grounded generation with local evidence, OR Google Search grounding.
  6. Escalate if needed: Returns safe escalation on NOT_FOUND: or missing evidence.

5.2 Gemini Wrapper (rag/gemini.py)

A thin, focused wrapper around the google-genai SDK. Every function does exactly one thing:

FunctionPurposeKey Details
embed_texts()Generate embeddingsSupports task type (RETRIEVAL_DOCUMENT vs RETRIEVAL_QUERY), batched
generate_grounded_answer()Generate from local evidenceTemperature 0.1, max 700 tokens
search_grounded_answer()Google Search grounding fallbackHandles 429 quota errors gracefully — returns empty instead of crashing
assess_conversation()Decide clarify vs answerJSON mode, returns structured action + extracted product details
identify_product_structured()Extract product entityJSON mode, returns ProductEntity dataclass

5.3 Vector Store (rag/retriever.py + rag/indexer.py)

Three ChromaDB collections with distinct purposes:

product_documents

Immutable official documentation. PDFs, Markdown, TXT files. Partitioned by product_id and optionally hardware_version. Never overwritten by user feedback.

approved_interactions

User-validated historical Q&A. Promoted via "Helpful" feedback. Secondary context — supplements but never replaces official docs.

general_support_faqs

Curated FAQ knowledge base. 686 Q&A pairs covering orders, returns, shipping, account management. No product/version filtering needed.

The product retriever uses $and metadata filtering when a hardware version is specified: {"$and": [{"product_id": id}, {"hardware_version": ver}]}. The FAQ retriever has no filtering — it searches all FAQ pairs by similarity.

5.4 Document Loader (rag/loader.py)

Parses file types with format-aware chunking:

  • PDF: Page-by-page extraction via PyPDF. If total text < 50 chars (scanned PDF), falls back to pytesseract OCR.
  • Markdown: Splits on heading patterns (# Heading or 1.2.3 Numbered). Preserves section titles as metadata.
  • TXT: Detects Q/A pair format (FAQ) via regex. Keeps question + answer as one chunk. Falls back to fixed-size chunking otherwise.

All formats use 400-word chunks with 50-word overlap. Every chunk carries full metadata: product_id, manufacturer, model, hardware_version, source_name, section, page.

5.5 FAQ Data Pipeline (scripts/prepare_faq_data.py)

Downloads and normalizes FAQ datasets from HuggingFace:

  • MakTek (200 pairs): Clean Q/A pairs for account, payments, orders, shipping, returns
  • Bitext (486 sampled from 26,872): Stratified sampling (18 per intent) including messy real-world phrasing with template placeholders replaced

Output: data/faq/general_support_faqs.jsonl — 686 curated pairs with category, intent, and source metadata.

5.6 Interactions & Feedback (rag/interactions.py)

Every non-clarification response is logged to data/interactions.jsonl with: question, answer, citations, escalation status, timestamps. When a user clicks "Helpful":

  1. Validates the answer wasn't an escalation
  2. Validates it has at least one citation
  3. Promotes the (question, answer, source URLs) tuple into the approved_interactions ChromaDB collection

This creates a self-improving memory loop — but critically, it never modifies the official documentation collection.

6. End-to-End Data Flow

A complete walkthrough of what happens from user input to final response.

1. InputUser types in Streamlit chat box
2. AssessGemini JSON: clarify or answer?
3. QueryBuild standalone retrieval string
4. RetrieveChromaDB vector search (top-5)
5. GateScore ≥ 0.42? Choose tier
6. GenerateGemini grounded answer
7. OutputRender with citations + feedback

Step-by-Step Walkthrough

Step 1: User Input

The user types a question in the Streamlit chat input. If they uploaded documentation or pasted a URL in the popover, the system auto-indexes it first (saves file → chunks → embeds → ChromaDB).

Step 2: Conversation Assessment

Gemini analyzes the latest message + recent history and returns structured JSON with an action field: "clarify" or "answer". If clarifying, it also returns exactly one short follow-up question (under 30 words). It extracts: product name, manufacturer, model, hardware version, confidence score.

Step 3: Standalone Query Formulation

The assistant concatenates: product name + hardware version + last 4 user turns + current question. This creates a self-contained retrieval query that doesn't depend on conversation history for context.

Step 4: Vector Search

Two parallel retrievals against ChromaDB:

  • retrieve_documents() — queries product_documents with optional hardware_version filtering
  • retrieve_approved_memory() — queries approved_interactions (top-2, no version filter)

Both use RETRIEVAL_QUERY task type. Scores are computed as 1 - cosine_distance.

Step 5: Relevance Gate

The best local chunk score is compared against MIN_DOCUMENT_SIMILARITY = 0.42:

Score ≥ 0.42

Local docs are relevant. Proceed to strict grounded generation with local evidence only.

Score < 0.42

Local docs insufficient. Fall through to Google Search grounding.

Step 6: Generation

Path A (local): A detailed prompt is assembled with the system instructions, all retrieved chunks (with source metadata), memory chunks, and the question. Gemini generates at temperature 0.1. If the output starts with NOT_FOUND:, escalation fires.

Path B (web): The question is sent to Gemini with the google_search tool enabled. Gemini searches official manufacturer pages and returns answers with API-verified citations.

Step 7: Response Assembly

A ChatResult is assembled with: answer text, up to 3 citations (title, URL, section, source type), flags (escalated, used_search, used_memory, clarification_needed). The interaction is logged to JSONL. The UI renders citations as inline badges and shows feedback buttons.

7. Safety, Guardrails & Escalation

How the system prevents giving wrong answers that could damage hardware.

7.1 The Three Safety Mechanisms

Mechanism 1: Strict System Prompt

The system prompt in SYSTEM_INSTRUCTIONS explicitly tells Gemini:

Use ONLY the supplied verified evidence. Never invent a specification,
procedure, reset sequence, or product feature.
If the evidence does not answer the question or if incompatible hardware
versions are mixed, respond exactly with NOT_FOUND: followed by a brief
explanation.

Temperature is set to 0.1 — very close to deterministic — to minimize creative drift.

Mechanism 2: Similarity Score Gate

Even if Gemini doesn't self-admit NOT_FOUND, the system checks: if the best retrieved chunk has a similarity score below 0.42, local generation is skipped entirely. The question goes to web search or escalation instead.

Mechanism 3: NOT_FOUND Detection

The output is checked for the NOT_FOUND: prefix. If present, it's stripped and replaced with a safe escalation message directing the user to official manufacturer support. This also applies to Google Search results — if the web search returns nothing useful, escalation fires.

7.2 The Escalation Response

When escalation triggers, the user sees:

"I couldn't verify an answer for TP-Link Archer AX21 (hardware version V2)
from approved documentation. To prevent incorrect hardware instructions,
please verify your model/version or check official manufacturer support."

Plus a citation link to the official support portal. The interaction is logged but never promoted to memory — preventing unverified information from entering the system.

7.3 Rate Limit Handling

Google Search grounding can hit 429 quota errors. The system catches these gracefully and falls through to escalation instead of crashing:

if "429" in exc_str or "quota" in exc_str or "rate" in exc_str:
    return "", []  # Falls through to escalation

9. RAG Methodology Deep Dive

The retrieval and generation methodology explained in detail.

9.1 Chunking Strategy

The system uses format-aware chunking, not one generic size for everything:

FormatChunking StrategyWhy
PDFPage-by-page, then 400 words / 50 overlapPage numbers preserved as metadata for citation
MarkdownSplit on headings (# Heading, 1.2.3 Numbered)Preserves document structure and section context
TXT (FAQ)Q/A pairs kept together as single chunksNever split a question from its answer
TXT (plain)400 words / 50 overlap fallbackOnly for unstructured long text
JSONL (General FAQs)Q/A pair as single document, category metadata686 pairs from MakTek + Bitext, embedded with RETRIEVAL_DOCUMENT

9.2 Embedding Strategy

  • Model: Gemini gemini-embedding-001 (768 dimensions)
  • Task types: Documents embedded with RETRIEVAL_DOCUMENT, queries with RETRIEVAL_QUERY — the model adjusts output based on the task.
  • Batching: 40 texts per API call to balance throughput and rate limits.
  • Critical rule: The same embedding model is used for indexing and querying. Mixing models silently breaks similarity search.

9.3 Dual-Path Evidence Retrieval

The system now routes questions to two independent pipelines based on domain classification:

Product Support Pipeline (hardware questions)

TierSourceWhen UsedCitation Type
1 — Local Docs product_documents collection Official manuals indexed for the product Document (title, section, page)
1b — Memory approved_interactions collection Prior verified Q&A pairs Verified historical Q&A
2 — Web Search Gemini Google Search Grounding Local docs missing or below threshold Web (API-verified URLs)
3 — Escalation Manufacturer support link No verified evidence from tiers 1-2 Support portal link

General Support Pipeline (account, orders, returns, etc.)

TierSourceWhen UsedCitation Type
1 — FAQ Collection general_support_faqs collection Curated Q&A pairs (686 from MakTek + Bitext) FAQ category (Returns, Shipping, etc.)
2 — Web Search Gemini Google Search Grounding FAQ collection below threshold or missing Web (API-verified URLs)
3 — General Escalation Customer support contact No verified evidence from tiers 1-2 Support contact link

Domain Classification

The conversation assessor (assess_conversation()) now outputs a question_domain field: "product_support" or "general_support". General support questions (account, orders, shipping, returns) are forced to action: "answer" — the system never asks for a product model when the question is about a return policy.

9.4 Prompt Engineering

The system prompt is carefully worded to enforce grounding:

You are a careful, version-aware product-support assistant.
Use ONLY the supplied verified evidence. Never invent a specification,
procedure, reset sequence, or product feature.
If the evidence does not answer the question or if incompatible hardware
versions are mixed, respond exactly with NOT_FOUND: followed by a brief
explanation.
Give concise, step-by-step instructions. Cite the exact source title,
section, or page number when answering from product documents.

The context assembled for generation includes two sections separated by headers: "Approved Historical Memory" (memory chunks) and "Official Product Documentation Evidence" (document chunks with full metadata).

9.5 Conversation Memory

The last 4 user turns are included in the retrieval query (for context) and in the generation prompt (as conversation context). Older turns are truncated — a simple fixed window avoids unbounded context growth.

10.2 Golden Question Evaluation

A benchmark set of questions in evaluation/golden_questions.csv with columns: id, product, hardware_version, question, answerable (yes/no). The CLI runner run_eval.py:

  1. Runs each question through ProductAssistant.answer()
  2. Checks answerable questions: must not be escalated AND must have ≥ 1 citation
  3. Checks unanswerable questions: must trigger escalation (not hallucinate)
  4. Reports pass/fail verdicts and writes them back to the CSV

Why this matters

The intentional "no" questions (no real answer in the knowledge base) test the escalation mechanism — the most important safety feature. If these pass as "answered," the system is hallucinating.

11. Key Design Trade-offs

What was chosen, what was deferred, and why.

DecisionChoseDeferredReasoning
Orchestration Custom module LlamaIndex / LangChain Full control, full explainability, no framework magic. More code but every line is meaningful.
Reranking Not implemented Cross-encoder reranker Quality improvement in production, but adds a model, dependency, and tuning surface. Chunk size tuning moves accuracy more per hour at this scale.
Cloud deployment Local prototype Docker, CI/CD, hosting Deliverable is a working prototype, not a hosted service. Ops maturity doesn't help the rubric.
Evaluation framework Custom CLI runner RAGAS pipeline Same signal (is the answer grounded?) without the setup overhead. Manual + CLI gets 80% of the value.
Streaming Full response + spinner Token-by-token streaming Perceived latency improvement, but st.write_stream + Gemini streaming adds complexity. Deferred to roadmap.
Model flexibility Gemini only Multi-model (Claude, GPT) Google Search grounding is Gemini-specific. Swapping models later is a targeted change thanks to the clean wrapper in gemini.py.
Memory validation Basic (escalation check + citation check) Multi-stage LLM judge, injection scanning Important for production, but the current gates catch the obvious failure modes. Complex validation deferred to roadmap.

The "Vibe-Coded" Advantage

Every architecture decision in this system is explicit and can be explained. There's no framework magic to hide behind. When asked "why does this work?", the answer is: "because here's the code that checks, here's the threshold, here's the prompt, and here's the fallback." That transparency is the real deliverable.

11.5. General Support FAQ Integration

The most recent major feature: adding a second knowledge domain for non-hardware questions.

The Problem

The original system only handled hardware troubleshooting. When a user asked "What is your return policy?" or "How do I reset my password?", the system would either:

  • Ask for a product model (wrong — return policies don't need a product)
  • Fall through to Google Search (expensive, unreliable)
  • Escalate to manufacturer support (wrong — this is a general question)

The Solution: Domain-Routed Dual Pipeline

Architecture Change

Before: Single linear pipeline
Assess → product_docs → Google Search → Escalation

After: Domain-routed dual pipeline
Assess (+ question_domain classification)
├── general_support → general_support_faqs → Google Search → General Escalation
└── product_support → product_docs + memory → Google Search → Hardware Escalation

Data Pipeline

The prepare_faq_data.py script downloads and normalizes FAQ datasets from HuggingFace:

SourceOriginal SizeSampledCategories
MakTek Customer Support FAQs200 pairsAll 200Account, payments, orders, shipping, returns
Bitext Customer Support Training26,872 pairs486 (18 per intent)Account, order, shipping, refunds, cancellations, and more

Total: 686 curated Q&A pairs stored in data/faq/general_support_faqs.jsonl.

Key Implementation Details

  • Auto-indexing: ensure_faq_index() in app.py runs on startup — checks if the FAQ collection is empty, indexes if needed. Cached with @st.cache_resource.
  • Domain classification: The assessor prompt now includes guidelines for classifying questions as product_support or general_support. General support questions are forced to action: "answer" — no product clarification.
  • Separate system prompt: FAQ_SYSTEM_INSTRUCTIONS is lighter than the hardware prompt — no version awareness needed, just clean FAQ grounding.
  • Different thresholds: FAQ similarity threshold is MIN_FAQ_SIMILARITY = 0.35 (lower than product docs at 0.42) because FAQ phrasing is more varied.
  • Category-based citations: FAQ answers cite the category (e.g., "Returns", "Shipping") rather than a specific document.
  • Separate escalation: _general_escalation() points to customer support, not manufacturer support.

No existing code was modified — only extended. This is exactly the "add a new domain" extensibility point mentioned in Section 12.3.

12.3 Architecture Extensibility

Every component is designed to be swappable independently:

  • Different LLM? Swap the google-genai calls in gemini.py.
  • Different vector store? Swap the chromadb.PersistentClient in retriever.py / indexer.py.
  • Different frontend? The rag/ module is a pure Python library — ProductAssistant.answer() takes a string and returns a ChatResult.
  • Add a reranker? Insert between retrieval and generation in chatbot.py.
  • Add a new domain? Create a new ChromaDB collection, add a retriever method, and route in the assessor.
